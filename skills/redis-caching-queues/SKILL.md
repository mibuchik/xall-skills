# Redis Caching Queues

Грамотное использование Redis: cache-aside с защитой от stampede, обязательные TTL, потоки (Streams), rate limiting и мягкая деградация.

## Когда применять
- Проектирование кэширования, очередей фоновых задач, распределённых блокировок и rate-limit в Redis
- Устранение cache stampede, переполнения памяти и рассинхронизации кэша

## Рабочий протокол
1. Задавай явный TTL с небольшим случайным jitter для каждого кэшируемого ключа, чтобы избежать одновременной лавины промахов.
2. Используй понятное пространство имён ключей с версией схемы (`v1:user:profile:{id}`), чтобы безболезненно менять формат.
3. Защищай тяжёлые промахи кэша (stampede) через singleflight / короткий mutex или фоновое раннее обновление.
4. Для очередей выбирай Redis Streams (`XADD`/`XREADGROUP`/`XACK`) с DLQ вместо хрупких `LPUSH`/`RPOP` без подтверждения.
5. Гарантируй, что при недоступности кэша приложение деградирует к БД с лимитом, а не падает 500-й ошибкой.

## Чеклист качества
- [ ] В продакшен-коде нигде не вызывается блокирующий `KEYS *` (только `SCAN`)
- [ ] Политика `maxmemory` и eviction (`allkeys-lru` для кэша, `noeviction` для очередей) разделены по инстансам
- [ ] Использован pipelining/Lua-скрипты для атомарных многошаговых операций

## Антипаттерны (чего избегать)
- Хранить кэш и критичные очереди в одном инстансе с `allkeys-lru` (вытеснит задачи!)
- Кэшировать огромные объекты целиком без инвалидации или лимита размера

## Верификация перед завершением
Протестируй cache hit/miss, отключение Redis и конкурентный burst на один горячий ключ.
