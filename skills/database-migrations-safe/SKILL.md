# Database Migrations Safe

Безопасные zero-downtime миграции БД: паттерн Expand-and-Contract, безопасные дефолты, бэкфилл батчами и обратимость.

## Когда применять
- Изменение схемы БД в продакшене: переименование/удаление колонок, смена типов, добавление NOT NULL
- Проверка SQL-миграций перед выкаткой на отсутствие длительных блокировок таблиц

## Рабочий протокол
1. Применяй Expand-and-Contract вместо прямого переименования/удаления: 1) добавь новую колонку (nullable), 2) пиши в обе (dual-write), 3) заполни старые строки батчами, 4) переключи чтение, 5) удали старую колонку в следующем релизе.
2. Добавляй ограничения `NOT NULL` / `CHECK` в PostgreSQL в 2 шага: `NOT VALID` -> `VALIDATE CONSTRAINT` (без блокировки записей).
3. Строй индексы через `CONCURRENTLY` вне транзакции и ставь жёсткий `lock_timeout` (например `3s`), чтобы миграция не встала в очередь и не заблокировала весь трафик.
4. Бэкфилль миллионы строк малыми батчами (1k–10k строк с паузой), никогда не делай один гигантский `UPDATE table SET ...`.
5. Проверяй совместимость старой версии приложения с новой схемой во время rolling deploy.

## Чеклист качества
- [ ] Миграция не держит `ACCESS EXCLUSIVE` блокировку дольше долей секунды
- [ ] Старый бинарник приложения продолжает работать сразу после применения миграции
- [ ] Есть проверенный план отката или безопасная компенсационная миграция

## Антипаттерны (чего избегать)
- Удалять колонку в том же релизе, в котором код ещё читает её со старых подов
- Менять тип колонки `INT -> BIGINT` в лоб на большой таблице под трафиком

## Верификация перед завершением
Прогони миграцию на копии схемы с тестовыми данными и проверь совместимость со старым и новым кодом.
