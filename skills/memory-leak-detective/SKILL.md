# Memory Leak Detective

Поиск и устранение утечек памяти (JS/Node/Electron, Python, JVM, native): 3-snapshot дифф кучи, граф удержания и контроль RSS.

## Когда применять
- Постепенный рост RSS/Heap со временем, OOM-киллы, замедление из-за частых GC-пауз
- Утечки подписок, таймеров, кэшей без eviction и незакрытых хендлов

## Рабочий протокол
1. Подтверди утечку под повторяемым сценарием: прогони N итераций, вызови GC и убедись, что память монотонно растёт (sawtooth с растущим дном).
2. Сделай метод 3 снимков кучи (Three-Snapshot technique): базовый -> после действия A -> после повтора A -> смотри объекты, созданные между #1 и #2 и выжившие к #3.
3. Проверь частых виновников: неснятые event listeners / IPC listeners, неограниченные `Map`/`dict` кэши, замыкания с ссылками на крупные буферы, незакрытые стримы/файлы.
4. Внедри явный cleanup (`removeListener`, `AbortController`, `WeakMap`, LRU-кэш с `maxSize`, context managers).
5. Перепрогони стресс-цикл и убедись, что плато RSS стабилизировалось.

## Чеклист качества
- [ ] Каждому `on`/`addEventListener`/`setInterval` соответствует парный cleanup при unmount/close
- [ ] Все in-memory кэши имеют жёсткий лимит размера или TTL
- [ ] После фикса 100+ циклов нагрузки не дают монотонного роста heap/RSS

## Антипаттерны (чего избегать)
- Путать нормальный кэш ОС / отложенный GC с утечкой без принудительного GC-прохода
- Просто увеличивать `--max-old-space-size` вместо поиска retaining path

## Верификация перед завершением
Сравни динамику RSS/heapUsed на 50–100 повторах сценария до и после исправления.
