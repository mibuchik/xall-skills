# API Design REST Graphql

Проектирование предсказуемых REST/OpenAPI и GraphQL контрактов: версионирование, идемпотентность, RFC 9457 ошибки и курсорная пагинация.

## Когда применять
- Проектирование новых HTTP/JSON или GraphQL API, контрактов и схем ошибок
- Ревью эндпоинтов на совместимость, пагинацию и идемпотентность

## Рабочий протокол
1. Определи ресурсы, инварианты и границы владения данными до выбора URL и методов.
2. Используй единый формат ошибок (RFC 9457 Problem Details: `type`, `title`, `status`, `detail`, `errors[]`) и стабильные машинные коды.
3. Для списков применяй курсорную пагинацию (`cursor`, `limit`, `next_cursor`) вместо нестабильного `OFFSET` на изменяемых таблицах.
4. Для мутирующих POST/платежей введи `Idempotency-Key` и чёткую семантику повторных запросов.
5. Зафиксируй контракт в OpenAPI 3.1 / GraphQL SDL и проверяй обратную совместимость на уровне CI.

## Чеклист качества
- [ ] Все входные поля имеют явные типы, ограничения длины/диапазона и валидируются на границе
- [ ] Статус-коды точны (`201 Created`, `204 No Content`, `409 Conflict`, `422 Unprocessable`, `429 Too Many Requests`)
- [ ] Версионирование и стратегия депрекации (Sunset/Deprecation headers) определены заранее

## Антипаттерны (чего избегать)
- Возвращать HTTP 200 с `{ ok: false, error: ... }` вместо реальных HTTP статусов
- Утекать внутреннюю схему БД напрямую в JSON-ответы без DTO/сериализатора

## Верификация перед завершением
Провалидируй OpenAPI/SDL схему и прогони контрактные тесты на валидные, граничные и ошибочные запросы.
