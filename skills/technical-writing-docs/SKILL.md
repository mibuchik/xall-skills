# Technical Writing Docs

Инженерная документация по Diátaxis: чёткое разделение туториалов, how-to гайдов, справочника API и архитектурных объяснений с проверенными примерами.

## Когда применять
- Написание документации проекта, гайдов онбординга, runbook, ADR и справочников API
- Переработка запутанных стен текста в ясные и сканируемые документы

## Рабочий протокол
1. Определи тип документа по Diátaxis и не смешивай всё в кучу: Tutorial (обучение), How-To (конкретная задача), Reference (точный справочник), Explanation (почему устроено именно так).
2. Начинай с 2-строчного ответа «что это и когда нужно», затем давай минимальный работающий пример (Quickstart за 60 секунд).
3. Проверяй КАЖДУЮ команду, флаг и фрагмент кода в реальной среде — устаревшая команда в доке хуже отсутствия доки.
4. Используй чёткие заголовки, таблицы параметров и короткие абзацы (2–4 строки), ссылайся на исходники и актуальные версии.
5. Для архитектурных решений оформляй краткий ADR (Context -> Decision -> Alternatives -> Consequences).

## Чеклист качества
- [ ] Все команды в примерах копируются и выполняются без правок
- [ ] Указаны реальные пререквизиты (версии ОС, Node/Bun/Python, сервисы)
- [ ] Нет канцелярита и раздутых вступлений ради объёма

## Антипаттерны (чего избегать)
- Документировать поведение «по памяти» без сверки с кодом
- Писать один 2000-строчный документ вместо структурированного оглавления

## Верификация перед завершением
Пройди Quickstart с нуля по собственному тексту и проверь каждую ссылку и команду.
