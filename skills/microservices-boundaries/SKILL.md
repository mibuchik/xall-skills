# Microservices Boundaries

Выделение ограниченных контекстов (DDD), выбор между модульным монолитом и сервисами, transactional outbox и устойчивость к сбоям сети.

## Когда применять
- Разделение монолита на модули/сервисы или проектирование межсервисного взаимодействия
- Борьба с распределёнными транзакциями, двойной записью и каскадными отказами

## Рабочий протокол
1. Начинай с модульного монолита: выделяй физический сервис только при независимом масштабировании, деплое, команде или изоляции сбоев.
2. Закрепи за каждым сервисом единоличное владение таблицами БД — никаких общих таблиц для записи из двух сервисов.
3. Замени распределённые 2PC-транзакции на Transactional Outbox + идемпотентных потребителей (dedup по `event_id`).
4. Добавь таймауты, ограниченные ретраи с exponential backoff + jitter и circuit breaker на все исходящие вызовы.
5. Протяни `trace_id` / `correlation_id` через все HTTP-заголовки и события очередей.

## Чеклист качества
- [ ] Нет синхронных цепочек длиннее 2–3 хопов на критическом пути запроса
- [ ] Каждый consumer безопасно переживает повторную доставку одного и того же события
- [ ] Контракты событий версионируются аддитивно (старые поля не ломаются)

## Антипаттерны (чего избегать)
- Распределённый монолит: сервисы нельзя задеплоить по отдельности без синхронного релиза
- Бесконечные ретраи без jitter, устраивающие DDoS собственному апстриму

## Верификация перед завершением
Смоделируй таймаут/отказ зависимости и дубликат сообщения — убедись, что состояние остаётся консистентным.
