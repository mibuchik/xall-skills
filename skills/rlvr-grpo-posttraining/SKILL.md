# RLVR GRPO Posttraining

Пост-обучение с проверяемыми наградами (RLVR, ReST-EM, Dr. GRPO, DAPO): надёжные песочницы-верификаторы, фильтрация по золотым решениям и защита от reward hacking.

## Когда применять
- Построение RLVR / ReST-EM / GRPO / DAPO пайплайнов для кодовых и математических LLM
- Отладка верификаторов, нулевой дисперсии наград и сваливания политики

## Рабочий протокол
1. ВСЕГДА прогоняй верификатор на gold-решениях датасета на CPU ДО старта GPU-раунда: если gold падает — чини парсер/нормализатор тестов, а не жги GPU.
2. Запускай сгенерированный код только в изолированном подпроцессе с жёсткими лимитами времени, памяти и без доступа к сети/хостовым файлам.
3. Отбрасывай группы с нулевой дисперсией (все K сэмплов 0 или все 1 — динамический сэмплинг DAPO) и убирай смещение длины (Dr. GRPO / token-level loss).
4. Отслеживай метрики E-step: `mastered`, `frontier` (0 < pass < 1), `hard_zero`, `empty` и среднюю длину `<think>` — падение `frontier` до 0 сигналит о баге верификатора.
5. Контролируй KL-дивергенцию и проверяй каждый раунд roll-forward гейтом на независимом executable бенчмарке.

## Чеклист качества
- [ ] Верификатор покрыт юнит-тестами (включая JSON-списки ассертов, синтаксические ошибки и таймауты)
- [ ] На gold-выборке верификатор даёт >= 90–100% прохождение до запуска RL
- [ ] Нет reward hacking (модель не может обойти тест пустым `exit(0)` или подменой assert)

## Антипаттерны (чего избегать)
- Запускать RLVR без предварительного CPU gold-check на реальных данных датасета
- Использовать `eval()` в основном процессе обучения вместо изолированного subprocess с таймаутом

## Верификация перед завершением
Запусти `pytest` на верификатор и CPU gold self-check на 20–50 задачах перед GPU-запуском.
