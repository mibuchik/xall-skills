# Regex Parsing Grammars

Безопасные регулярные выражения и парсеры: защита от катастрофического бэктрекинга (ReDoS), читаемые `VERBOSE` паттерны и своевременный переход к AST/токенизатору.

## Когда применять
- Написание сложных регулярных выражений, лексеров, парсеров конфигов, логов, Markdown и diff
- Диагностика зависаний CPU из-за ReDoS и хрупких строковых разборов

## Рабочий протокол
1. Оцени сложность грамматики: плоские токены/строки -> regex; вложенные скобки, блоки, экранированные кавычки, HTML/JSON/код -> настоящий лексер/рекурсивный парсер или AST.
2. Избегай вложенных квантификаторов `(a+)+`, `(a|aa)+` и перекрывающихся альтернатив — они вызывают экспоненциальный ReDoS на длинном несовпадающем вводе.
3. Используй якорные границы (`^`, `$`, `\b`), именованные группы `(?P<name>...)` / `(?<name>...)` и флаг `VERBOSE`/`x` с комментариями для сложных паттернов.
4. Компилируй горячие регулярки один раз на уровне модуля, а не внутри цикла.
5. Покрывай каждый паттерн тестами: валидные случаи, краевые случаи (пустая строка, Unicode, CRLF) и adversarial длинная строка (10K символов) с проверкой времени < 10ms.

## Чеклист качества
- [ ] Ни один regex не зависает на adversarial-строке длиной 10 000+ символов
- [ ] Обработаны оба варианта переводов строк (`\n` и `\r\n`) и Unicode-текст
- [ ] Вложенные структуры разбираются парсером/стеком, а не хрупким регэкспом

## Антипаттерны (чего избегать)
- Пытаться распарсить рекурсивный JSON, Markdown с вложенными блоками или Python-код одной регуляркой
- Писать нечитаемую 180-символьную строку regex без тестов и комментариев

## Верификация перед завершением
Прогони юнит-тесты включая длинный несовпадающий ввод с ассертом времени выполнения.
