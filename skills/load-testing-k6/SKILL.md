# Load Testing K6

Нагрузочное и стресс-тестирование сервисов (k6 / Locust / Vegeta): профили нагрузки, SLO-пороги, выявление точки насыщения и деградации.

## Когда применять
- Проверка пропускной способности API, вебсокетов или очередей перед релизом
- Определение предела одновременных пользователей, пулов БД и деградации под спайками

## Рабочий протокол
1. Зафиксируй целевые SLO до запуска: RPS, p95/p99 latency, error rate (< 0.1–1%) и лимиты CPU/RAM/DB connections.
2. Выбери профиль нагрузки: Smoke (1–5 VU), Load (целевой трафик), Stress (ступенчатый рост до точки перелома), Spike (резкий всплеск), Soak (длительный прогон на утечки).
3. Используй реалистичное распределение данных и сценариев (не долби один и тот же кэшированный GET `/health`).
4. Настрой автоматические `thresholds` в k6/Locust и собирай метрики сервера параллельно с клиентом.
5. Определи узкий ресурс в точке насыщения (CPU, пул соединений, диск, локи) и оформи отчёт с конкретным планом запаса мощности.

## Чеклист качества
- [ ] Генератор нагрузки сам не упёрся в CPU/сокеты/ulimit (нет coordinated omission)
- [ ] Пороги p95/p99 и error rate явно закодированы в скрипте теста
- [ ] Тестируется изолированное окружение, не продакшен-пользователи

## Антипаттерны (чего избегать)
- Делать выводы по 5-секундному запуску `ab` без прогрева JIT/кэшей
- Игнорировать рост очередей и HTTP 5xx/таймаутов, глядя только на успешный RPS

## Верификация перед завершением
Запусти smoke + ramp-up сценарий, сохрани JSON-сводку квантилей и проверь срабатывание thresholds.
