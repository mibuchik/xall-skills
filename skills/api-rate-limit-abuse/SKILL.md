# API Rate Limit Abuse

Защита API от злоупотреблений и исчерпания ресурсов: token-bucket/sliding-window rate limiting, лимиты размера тела, таймауты и заголовки `Retry-After`.

## Когда применять
- Защита публичных и LLM-эндпоинтов от перебора, флуда, дорогих запросов и исчерпания CPU/GPU
- Проектирование квот, очередей и ограничений на загрузку файлов

## Рабочий протокол
1. Применяй многоуровневые лимиты: жёсткий лимит на auth/дорогие операции (LLM, поиск, экспорт) + общий лимит на IP/API-ключ/пользователя.
2. Ограничивай размер входного тела (`max_body_bytes`), глубину JSON, длину массивов и `max_tokens` ДО начала обработки.
3. Возвращай честный `429 Too Many Requests` с заголовками `Retry-After` и `RateLimit-*`, чтобы корректные клиенты замедлялись.
4. Для тяжёлых ресурсов (например, 1 GPU) используй явный семафор/очередь с ограниченной длиной и быстрым отказом `503`/`429` при переполнении.
5. Проверяй, что `X-Forwarded-For` нельзя подделать напрямую (доверяй только числу хопов доверенного прокси).

## Чеклист качества
- [ ] Нет незащищённых эндпоинтов с неограниченным `limit=9999999` или без лимита тела запроса
- [ ] Перегрузка возвращает `429`/`503` быстро, а не кладёт сервер по OOM
- [ ] Обычные легитимные burst-запросы проходят комфортно благодаря token bucket

## Антипаттерны (чего избегать)
- Ставить один общий лимит по `X-Forwarded-For`, который любой клиент подделывает случайным заголовком
- Считать лимиты только на клиенте без серверного контроля

## Верификация перед завершением
Напиши тест на превышение лимита (`429` + `Retry-After`) и на отклонение слишком большого тела (`413`).
