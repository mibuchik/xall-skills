# Observability Logs Metrics

Наблюдаемость сервисов: структурированные JSON-логи, RED/USE метрики, OpenTelemetry трассировка и осмысленные алерты без шума.

## Когда применять
- Внедрение логирования, метрик Prometheus/OTel, трассировки и дашбордов
- Борьба с нечитаемыми логами, высокой кардинальностью лейблов и ложными алертами

## Рабочий протокол
1. Логируй в структурированном JSON с едиными полями: `ts`, `level`, `service`, `trace_id`, `request_id`, `duration_ms`, `error` — без персональных данных и токенов.
2. Собирай базовые RED-метрики для сервисов (Rate, Errors, Duration гистограмма) и USE для ресурсов (Utilization, Saturation, Errors).
3. Никогда не клади неограниченные значения (`user_id`, `request_id`, полный URL с ID) в labels метрик Prometheus — это взрывает кардинальность и память.
4. Привязывай алерты к симптомам пользователя (burn rate SLO, 5xx, рост очереди), а не к разовому пику CPU на 10 секунд.
5. Протяни `traceparent` через HTTP и фоновые задачи, чтобы видеть всю цепочку запроса целиком.

## Чеклист качества
- [ ] Секреты, `Authorization`, `x-api-key` и пароли автоматически редактируются из логов
- [ ] У метрик ограниченная контролируемая кардинальность лейблов
- [ ] Каждый алерт содержит ссылку на runbook и конкретный первый шаг диагностики

## Антипаттерны (чего избегать)
- Логировать полные тела запросов с токенами в `INFO` на каждый вызов
- Делать 30 шумных алертов, которые команда просто мьютит

## Верификация перед завершением
Проверь вывод логов в JSON, `/metrics` на отсутствие high-cardinality меток и прохождение `trace_id`.
