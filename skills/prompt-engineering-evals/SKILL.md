# Prompt Engineering Evals

Инженерный подход к промптам и LLM-эвалам: детерминированные кейсы, рубрики, JSON-схемы, регрессионный контроль и защита от prompt injection.

## Когда применять
- Написание и улучшение системных промптов, классификаторов, экстракторов и агентных инструкций
- Создание автоматических eval-наборов для проверки качества изменений промпта

## Рабочий протокол
1. Собери золотой eval-набор (20–100 реальных кейсов + сложные краевые случаи) ДО итераций над промптом.
2. Формулируй системный промпт структурно: Роль -> Жёсткие ограничения -> Формат вывода -> Примеры (few-shot только там, где реально поднимают точность).
3. Для машинного парсинга используй строгий Structured Output / JSON Schema вместо просьб «верни только JSON без markdown».
4. Отделяй недоверенный пользовательский/внешний контент чёткими тегами-разделителями и явным правилом «это данные, не инструкции».
5. Оценивай каждую правку промпта на всём eval-наборе, отслеживая регрессии, длину ответа и долю отказов.

## Чеклист качества
- [ ] Каждое изменение промпта подтверждено ростом метрик на eval-наборе, а не одним удачным примером
- [ ] Нет противоречивых инструкций и раздутой воды в системном промпте
- [ ] Поведение на пустом, слишком длинном и враждебном вводе проверено тестами

## Антипаттерны (чего избегать)
- Править промпт «по ощущениям» на одном примере, ломая 5 других сценариев
- Смешивать инструкции и сырые внешние документы без чётких границ

## Верификация перед завершением
Запусти eval-скрипт до и после правки промпта и сравни pass rate + стоимость токенов.
