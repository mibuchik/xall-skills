# GGUF Quantization Llamacpp

Квантизация и локальный инференс LLM в llama.cpp: калибровка `llama-imatrix`, выбор Q4/Q5/Q6/Q8, KV-кэш квантизация и замер tok/s + качества.

## Когда применять
- Конвертация BF16 -> GGUF, расчёт imatrix и настройка `llama-server` под локальный GPU
- Балансировка VRAM, длины контекста (32K–128K), скорости генерации и деградации качества

## Рабочий протокол
1. Конвертируй модель в F16/BF16 GGUF, проверяя метаданные токенайзера и шаблон чата.
2. Построй importance matrix (`llama-imatrix`) на репрезентативном калибровочном корпусе (код + рассуждения + целевой язык, 60–100 чанков), прежде чем квантовать в `Q4_K_M`/`Q5_K_M`.
3. Оценивай бюджет VRAM: веса + KV-кэш (учитывай GQA и квантизацию KV `q8_0`/`q4_0` или TurboQuant) + compute buffer (~1–1.5 GB запаса).
4. Выставляй рекомендуемые параметры сэмплинга для reasoning-моделей (`temp`, `top_p`, `min_p`, `repeat_penalty`), избегая жадного `temp=0` там, где модель зацикливается.
5. Прогоняй perplexity / кодовый smoke-eval и замер `prompt eval` / `eval tok/s` на каждом новом GGUF.

## Чеклист качества
- [ ] Использована свежая `imatrix` для финальной квантизации (особенно критично для <= Q5 и MoE)
- [ ] Нет частичного offload важных слоёв на CPU, если вся модель помещается в VRAM
- [ ] Проверены остановка по EOS-токену и корректность `<think>...</think>` на реальных промптах

## Антипаттерны (чего избегать)
- Квантовать 4-bit/5-bit без `imatrix` на узкоспециализированных кодовых моделях
- Забывать зарезервировать VRAM под KV-кэш на длинном контексте, ловя внезапный OOM

## Верификация перед завершением
Проверь загрузку в `llama-server`, замерь `tok/s`, VRAM usage и прогони контрольный тест качества.
