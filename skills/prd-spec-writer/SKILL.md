# PRD Spec Writer

Написание чётких продуктовых и технических спецификаций (PRD/RFC): цель и анти-цели (Non-Goals), пользовательские сценарии, краевые случаи и критерии приёмки.

## Когда применять
- Формальная постановка фичи, PRD, RFC или техзадания перед началом разработки
- Устранение размытых требований и скрытых допущений до написания кода

## Рабочий протокол
1. Сформулируй Problem Statement (какую конкретную боль решаем и для кого) и раздел Non-Goals (что осознанно НЕ делаем в этой итерации — защита от scope creep!).
2. Опиши сквозные пользовательские сценарии (happy path + пустые состояния + ошибки + права доступа).
3. Зафиксируй технические контракты (данные, API/IPC, ограничения производительности, безопасность и миграции).
4. Выпиши проверяемые критерии приёмки (Acceptance Criteria) в формате Given / When / Then — каждый пункт можно превратить в тест.
5. Добавь таблицу открытых вопросов и рисков с конкретным планом закрытия.

## Чеклист качества
- [ ] Раздел Non-Goals явно очерчивает границы версии v1
- [ ] Нет размытых формулировок вроде «должно работать быстро и красиво» — указаны измеримые критерии
- [ ] Продуманы пустые состояния, оффлайн/ошибки и откат

## Антипаттерны (чего избегать)
- Писать спецификацию без раздела «чего мы НЕ делаем»
- Смешивать требования бизнеса и случайные детали реализации без объяснения «почему»

## Верификация перед завершением
Проверь, что другой инженер сможет реализовать и протестировать фичу по спецификации без догадок.
